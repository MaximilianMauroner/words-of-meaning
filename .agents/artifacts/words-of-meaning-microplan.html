Words of Meaning

A local blind prompt-identification benchmark for measuring whether qualitative words leave detectable behavioral signatures in generated source code.

Microplan prepared 31 August 2026. First implementation milestone includes blind identification and control-relative behavioral profiles.

Claim boundary. The benchmark can show that an adjective changed observable output in a recognizable way. It cannot establish that a model holds a particular hidden definition of that adjective.

Goal and definition of done

Build a local, single-user React application that runs controlled source-generation experiments through the TypeScript Codex SDK. The app must hide the true condition during judging, prevent one run from inheriting another run's messages or workspace, and keep enough raw evidence to audit every metric.

Done criteria

  • A user can enter a base prompt containing {{word}}, add at least two words, keep the required no-word control, choose run count and model settings, and start an experiment.
  • The default example can run six conditions with five independent generations per condition, for 30 source bundles total.
  • Every generation, classification, and profile evaluation starts in a new OS process, new Codex SDK instance, new SDK thread, and unique temporary working directory.
  • No judgment job receives the true condition, generation prompt, generator transcript, generation thread ID, or stable ordering that reveals the answer.
  • The result screen reports chance baseline, top-1 accuracy, log loss, per-condition recall, control detection, a count-based confusion matrix, probability summaries, behavioral profiles, and raw run details.
  • Interrupted experiments resume pending work without rerunning successful jobs. Cancellation stops new jobs and preserves completed results.
  • Automated tests prove prompt construction, source normalization, seeded shuffling, score calculations, database constraints, blind payload construction, process isolation, and workspace isolation.

Confirmed scope

Deferred

Account caveat. The SDK will reuse the local Codex sign-in. The app will not request or store an API key. Existing account entitlements, credits, rate limits, and fair-use rules still apply. The official documentation does not promise that every SDK run is free of account usage limits.

The plan uses the documented TypeScript package @openai/codex-sdk. Official documentation says it runs server-side on Node 18 or newer, starts work with startThread(), and continues history when callers reuse a thread. See Codex SDK documentation.

System design

Process contract

The parent scheduler reads SQLite and owns the truth. It sends a narrow JSON envelope to a child over standard input. Generation envelopes contain the rendered prompt and settings. Classification envelopes contain the adjective-free task, canonical source bundle, and randomized candidate labels. Profile envelopes contain the adjective-free task, source bundle, rubric, and dimensions. Child processes cannot open the experiment database.

Each child writes one validated JSON result to standard output. Diagnostic events go to standard error with secrets and source content redacted. The parent stores the result, exit code, timing, model, reasoning effort, SDK version, and a hash of the input envelope.

Job state machine

pending -> leased -> running -> succeeded
                    |          |
                    |          +-> failed_retryable -> pending
                    +-------------> failed_final

experiment: draft -> queued -> running -> completed
                              |          |
                              +-> canceled
                              +-> completed_with_failures

Leases have an expiry. On startup, the scheduler returns expired leased or running jobs to pending. It never overwrites a successful attempt.

Run isolation and contamination controls

This is a correctness property of the benchmark. A fresh prompt alone is not enough.

Honest limit. Separate threads prevent history reuse, but all runs still use the same installed SDK, account, model, and permitted machine-level Codex configuration. Those shared constants are part of the experiment environment. The app records them and blocks known mutable cross-run channels; it does not claim to isolate unobservable provider-side state.

Temporary workspace lifecycle

  1. Create the directory with mode 0700 under the operating system's temporary root.
  2. Write only the job envelope's scaffold or evaluator input.
  3. Start Codex with workspace access limited to that directory and network disabled unless an experiment explicitly requires package retrieval in a later milestone.
  4. Collect allowed output files, normalize them, hash the bundle, and persist the bundle transactionally.
  5. Remove the temporary directory in a finally block. On cleanup failure, quarantine the path and show a local warning without feeding it to another run.

Experiment contract

Prompt rendering

The base prompt must contain exactly one {{word}} placeholder. A word condition replaces it with the entered word. The control replaces it with an empty string, then normalizes whitespace and punctuation around the removed slot. The preview shows every rendered prompt before execution.

The generator also receives a fixed artifact contract: create the requested implementation inside the current workspace, do not mention or encode the qualitative modifier, do not add prose files unless the task requests them, and finish without reading outside the workspace. The app stores the full fixed contract by version so later experiments remain comparable.

Canonical source bundle

  • Include UTF-8 text files matching a configurable source allowlist such as .ts, .tsx, .js, .jsx, .css, .json, and .md.
  • Exclude version-control data, dependency directories, build output, lockfiles by default, binary files, SDK transcripts, hidden Codex files, and files that exceed limits.
  • Sort relative paths bytewise. Normalize line endings to LF. Preserve source text otherwise.
  • Represent each file with a neutral ordinal path if the task lets models choose revealing names. Store the original path separately for owner inspection, never for judges.
  • Apply per-file and total byte limits. Mark truncated or rejected artifacts as failed generation attempts rather than silently scoring partial work.
  • Scan bundle text for the exact condition word, case-insensitively. If found, flag the run and exclude it from primary metrics by default because the judge could answer by string matching. Keep it visible in the audit view.

Classification output

{
  "prediction": "polished",
  "modifier_present_probability": 0.91,
  "probabilities": {
    "control": 0.03,
    "lovely": 0.08,
    "beautiful": 0.17,
    "elegant": 0.12,
    "polished": 0.51,
    "refined": 0.09
  }
}

Labels must match the supplied candidates exactly. Values must be finite and fall between 0 and 1. Candidate probabilities must sum to 1 within 0.001, and prediction must be an argmax. The parent rejects invalid JSON. A retry starts a different process and thread while retaining the failed attempt.

Behavioral profile output

Each profile call scores fixed dimensions from 1 to 7 and may return null only when the source lacks evidence. Default dimensions are simplicity, abstraction, visual ornamentation, consistency, UX detail, code verbosity, defensive programming, modularity, dependency count, documentation, type strictness, and accessibility. Each dimension has anchored descriptions for 1, 4, and 7. Rubric versions are immutable once an experiment starts.

The app displays a condition's mean raw score minus the control mean for that dimension. It also shows sample count, standard deviation, and the raw distributions. The control line is zero by construction, not an evaluator output.

Metrics and interpretation

MetricDefinitionWhy it is present
Chance baseline1 / candidate_count, including controlFrames top-1 accuracy against random choice.
Top-1 accuracyCorrect predictions divided by eligible judgmentsDirect identifiability measure.
Per-condition recallCorrect predictions for a condition divided by eligible outputs from that conditionShows which words produce recognizable signatures.
Confusion matrixRaw counts by actual and predicted label, with optional row percentagesReveals pairs that collapse into similar instructions.
Log lossNegative mean log probability assigned to the true label, with probability floor 1e-12Uses the complete probability distribution and penalizes confident mistakes.
Control discriminationControl recall, modifier-present ROC summary when sample size permits, and mean modifier-present probability by conditionTests whether any qualitative modifier is detectable.
Pair confusionBidirectional off-diagonal count for each pairRanks the most commonly confused words.
Profile deltaCondition mean minus control mean by dimensionDescribes the observable direction associated with each word.

Primary metrics exclude failed calls, invalid artifacts, and direct word leaks, and show the excluded count beside every denominator. A secondary all-completed view may include flagged word leaks. With five runs per condition, the UI warns that one result moves per-condition accuracy by 20 percentage points. It recommends 20 to 50 runs for claims beyond tool development.

Milestone one reports descriptive results and does not label a word as statistically distinct. A later analysis milestone can add bootstrap intervals, permutation tests, multiple-comparison correction, and repeated judges.

User experience

Experiment builder

  1. Enter experiment name and base prompt. The editor validates one {{word}} slot and previews the adjective-free task.
  2. Add words. The fixed control appears as a locked row. Duplicate and empty entries fail validation.
  3. Set generations per condition, generator model, judge model, reasoning efforts, maximum concurrency, and profile dimensions.
  4. Review rendered prompts, total model-call count, account-usage warning, isolation audit, and estimated stages.
  5. Start the experiment. Configuration becomes immutable; "Duplicate experiment" creates an editable copy.

Progress screen

Show totals for generation, classification, and profiles; current concurrency; retry counts; elapsed time; cancellation; and failures. Stream status with server-sent events and fall back to polling. Never stream hidden words beside judgment jobs.

Results screen

  • Summary cards for accuracy, chance, log loss, control recall, exclusions, and completed sample count.
  • Ranked most and least identifiable conditions with exact denominators.
  • Confusion matrix with count and row-percentage modes.
  • Most-confused pairs.
  • Behavioral profile table or compact diverging chart, always paired with raw score distributions.
  • Condition detail with all runs, canonical source, prediction, probabilities, modifier probability, profile values, flags, attempt history, and copied hashes.
  • Export of experiment configuration, raw results, and metric inputs as JSON. Export excludes local auth data, temporary paths, and full SDK diagnostics.

Implementation sequence

  1. Prove the SDK boundary. Create a throwaway TypeScript probe that reuses the current Codex sign-in, starts one thread, runs in a supplied temporary directory, applies the intended sandbox, returns structured text, and exits. Record the installed SDK behavior. Stop implementation if workspace restriction or fresh-thread guarantees cannot be observed.
  2. Create the application shell. Initialize Next.js, TypeScript strict mode, linting, tests, Drizzle, SQLite, and server-only module guards. Add health and preflight endpoints.
  3. Implement the domain model. Add migrations, experiment validation, Unicode-normalized conditions, mandatory control, immutable started configurations, job transitions, leases, retries, and restart recovery.
  4. Build the isolated runner. Add the parent scheduler, child entry point, narrow envelope types, environment allowlist, temporary workspace manager, SDK adapter, timeout and cancellation handling, result validation, cleanup, and redacted diagnostics.
  5. Generate artifacts. Render prompts, copy a fixed minimal scaffold, run one Codex call, canonicalize allowed source files, detect direct word leaks, hash bundles, and persist artifacts.
  6. Add blind evaluators. Derive randomized candidate orders, build truth-free envelopes, validate classification probabilities, score fixed behavioral dimensions, and retain every failed attempt without exposing truth to retry prompts.
  7. Calculate results. Implement pure metric functions with fixture datasets, explicit denominators, exclusions, profile deltas, and stable JSON export.
  8. Build the UI. Add experiment builder, call-count preview, isolation audit, progress, cancellation, results, confusion matrix, profiles, source viewer, flags, attempts, and export.
  9. Harden and calibrate. Run contamination canaries, truth-leak snapshots, crash recovery tests, concurrency stress, malformed-output retries, and a small real-model smoke experiment. Inspect all raw payloads before accepting the benchmark.
  10. Document interpretation. Explain what identifiability supports, what it does not support, why the control matters, how exclusions work, and why five runs are development evidence rather than a firm conclusion.

Isolation acceptance canaries

  1. Run A receives a random 128-bit token in a file. Run B receives no token. Exact or normalized token presence in B fails the suite.
  2. Run A mutates a test SDK adapter's module global. Run B must observe its default value because it starts in another process.
  3. The application repository contains a test AGENTS.md instruction with a trap phrase. A child working outside the repository must not repeat it.
  4. A fake database row contains the true word in every truth-bearing field. Serialized judgment envelopes must remain byte-for-byte free of that word and its condition identifier.
  5. Thirty calls must yield 30 unique process/workspace pairs and 30 unique nonempty SDK thread IDs. Missing IDs fail the audit instead of being treated as proof.

Acceptance walkthrough

  1. Open the app and pass the Codex sign-in and isolation preflight.
  2. Create the React settings-page experiment with five words plus the locked control and five runs per condition.
  3. Confirm the preview shows 30 generation calls, 30 classification calls, 30 profile calls, and the final candidate list in no stable answer position.
  4. Start, stop the app midway, restart it, and verify only unfinished or expired jobs resume.
  5. Open the completed result. Confirm raw confusion counts add to the eligible judgment count and displayed percentages use the shown denominators.
  6. Inspect one judgment payload from each condition. None may contain truth or generator-only metadata.
  7. Inspect attempt records. Every model call must have a unique process/workspace pair and thread ID.
  8. Open a word detail page and compare its five source bundles, probability distributions, and control-relative profiles.
  9. Export JSON and recompute accuracy and matrix counts with the test utility. Results must match the UI.
  10. Run the contamination canary suite. Any failure blocks release.
